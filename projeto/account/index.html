    Account

    Repositórios: pna26/account (interface) e pna26/account-service (implementação)

    Página completa do grupo: Account

    O Account é o dono do cadastro de contas da loja. Ele:

    1. cria, lista, busca e apaga contas (/accounts);
    2. guarda a senha só como hash (a senha nunca é salva nem devolvida);
    3. confere e-mail e senha no login, a pedido do Auth (POST /accounts/login);
    4. grava o papel da conta (USER/ADMIN), usado pelo RBAC;
    5. registra um evento AccountCreated no outbox, na mesma transação da conta, para a mensageria.

    É um serviço Spring Boot (Web MVC) + Spring Data JPA sobre PostgreSQL, com o schema criado pelo Flyway. Segue o Hands-on 1 do curso, com a rota de login do Hands-on 3.

    Dois repositórios: interface e implementação

    Como no curso, o serviço tem dois repositórios:

    Repositório Conteúdo Quem usa
    account AccountController (interface com as rotas, anotada com @FeignClient) e os DTOs AccountIn e AccountOut o account-service (implementa) e o auth-service (chama)

    A interface vira uma biblioteca Maven (store:account:1.0.0). O contrato fica num lugar só: o AccountResource implementa o AccountController, e o Auth usa a mesma interface como cliente Feign. Se uma rota mudar, os dois lados param de compilar até serem atualizados.

    package store.account;

import java.util.List;

import org.springframework.cloud.openfeign.FeignClient;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;

@FeignClient(
    name="account",
    url="http://account:8080"
)
public interface AccountController {

    @PostMapping("/accounts")
    public ResponseEntity<Void> create(
        @RequestBody AccountIn in
    );

    @GetMapping("/accounts")
    public ResponseEntity<List<AccountOut>> findAll();

    @DeleteMapping("/accounts/{id}")
    public ResponseEntity<Void> delete(
        @PathVariable String id
    );

    @GetMapping("/accounts/health-check")
    public ResponseEntity<Void> healthCheck();

    @GetMapping("/accounts/{id}")
    public ResponseEntity<AccountOut> findById(
        @PathVariable String id
    );

    @PostMapping("/accounts/login")
    public ResponseEntity<AccountOut> login(
        @RequestBody AccountIn in
    );

}

    Rotas

    Método Rota Entrada Saída
    POST /accounts { name, email, password } 201 + Location: /accounts/{id}
    GET /accounts — [{ id, name, email, role }]
    GET /accounts/{id} — { id, name, email, role } ou 404
    DELETE /accounts/{id} — 204
    POST /accounts/login { email, password } { id, name, email, role } ou 401 (interno: quem chama é o Auth)

    Pelo gateway, todas as rotas de /accounts/** exigem o cookie do token e passam pelo RBAC. Para criar conta sem estar logado, o caminho é o POST /auth/register do Auth.

    package store.account;

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.Base64;
import java.util.List;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.web.server.ResponseStatusException;

import store.account.outbox.Outbox;

@Service
public class AccountService {

    @Autowired
    private AccountRepository accountRepository;

    @Autowired
    private Outbox outbox;

    // conta e evento AccountCreated na mesma transação (transactional outbox):
    // ou os dois são gravados, ou nenhum (ex.: e-mail duplicado desfaz tudo)
    @Transactional
    public Account create(Account account) {

        if (null == account.password()) {
            throw new ResponseStatusException(
                HttpStatus.BAD_REQUEST, "Password is empty"
            );
        }

        final String pass = account.password().trim();
        if (pass.length() < 6) {
            throw new ResponseStatusException(
                HttpStatus.BAD_REQUEST, "Password must have at least 6 characters"
            );
        }

        if (account.email() == null || account.email().trim().isEmpty()) {
            throw new ResponseStatusException(
                HttpStatus.BAD_REQUEST, "Email is empty"
            );
        }

        account.hashPassword(calcHash(pass));
        // RBAC: toda conta nova é USER; o papel nunca vem da requisição
        account.role(Role.USER.name());

        final Account saved = accountRepository.save(
            new AccountModel(account)
        ).to();

        final AccountEvent event = AccountEvent.created(saved);
        outbox.append(event.eventId(), "account", saved.id(), event.eventType(), event);

        return saved;
    }

    public Account findById(String id) {
        // null quando o id não existe: o AccountResource responde 404
        return accountRepository.findById(id)
            .map(AccountModel::to)
            .orElse(null);
    }

    public void delete(String id) {
        accountRepository.deleteById(id);
    }

    public List<Account> findAll() {
        return accountRepository.findAll().stream()
            .map(AccountModel::to)
            .toList();
    }

    public Account findByEmailAndPassword(String email, String password) {

        if (password == null || password.isEmpty()) {
            throw new ResponseStatusException(
                HttpStatus.BAD_REQUEST, "Password is empty"
            );
        }

        final String hash = calcHash(password.trim());
        return accountRepository.findByEmailAndHashPassword(email, hash)
            .map(AccountModel::to)
            .orElseThrow(() -> new ResponseStatusException(
                HttpStatus.UNAUTHORIZED, "Invalid credentials"
            ));

    }

    private String calcHash(String text) {
        try {
            MessageDigest md = MessageDigest.getInstance("SHA-256");
            md.update(text.getBytes(StandardCharsets.UTF_8));
            byte[] digest = md.digest();
            return Base64.getEncoder().encodeToString(digest);
        } catch (NoSuchAlgorithmException e) {
            throw new ResponseStatusException(HttpStatus.INTERNAL_SERVER_ERROR, e.getMessage());
        }
    }

}

    O login faz o caminho inverso: calcula o hash da senha recebida e procura uma conta com aquele e-mail e aquele hash. Se não achar, responde 401 sem dizer se o erro foi no e-mail ou na senha.

    Banco (Flyway)

    As migrations criam o schema e evoluem a tabela sem mexer à mão no banco:

    V2026.08.24.002__create_table.sql
    CREATE TABLE accounts.accounts (
    id VARCHAR(36) PRIMARY KEY,
    name VARCHAR(256) NOT NULL,
    email VARCHAR(256) NOT NULL UNIQUE,
    hash_password VARCHAR(256) NOT NULL
);
    V2026.11.08.001__create_outbox.sql
    -- Transactional outbox (Hands-on 7 do curso): o evento é gravado na MESMA
-- transação que a conta. O OutboxRelay lê as linhas não publicadas e as envia
-- ao Kafka; se o Kafka estiver fora, elas esperam aqui e nada se perde.
CREATE TABLE accounts.outbox (
    id             UUID         PRIMARY KEY,
    aggregate_type VARCHAR(50)  NOT NULL,
    aggregate_id   VARCHAR(36)  NOT NULL,
    event_type     VARCHAR(50)  NOT NULL,
    payload        JSONB        NOT NULL,
    created_at     TIMESTAMPTZ  NOT NULL DEFAULT clock_timestamp(),
    published_at   TIMESTAMPTZ
);

-- o relay só olha as linhas ainda não publicadas: índice parcial pequeno
CREATE INDEX outbox_unpublished ON accounts.outbox (created_at) WHERE published_at IS NULL;
    V2026.11.16.001__add_role.sql
    -- Bottleneck: autenticação e autorização (RBAC).
-- Toda conta nasce USER; ADMIN só por promoção direta no banco (a API nunca
-- aceita o papel na entrada, então ninguém se autopromove).
ALTER TABLE accounts.accounts
    ADD COLUMN role VARCHAR(16) NOT NULL DEFAULT 'USER'
    CONSTRAINT accounts_role_check CHECK (role IN ('USER', 'ADMIN'));

    No compose o banco é um postgres:17; no EKS é o RDS PostgreSQL rds-store (ver EKS). Só o DATABASE_HOST do ConfigMap muda.

    Como foi testado

    • Todas as rotas no compose local (cadastro, listagem, busca, 404, DELETE, login certo e errado).
    • Pelo gateway: cadastro e login de ponta a ponta no scripts/smoke-test.sh, que roda no CI a cada push.
    • No EKS: o Flyway criou o schema no RDS no primeiro deploy (08/11) e o CI fez o deploy sozinho em 16/11.

    Limitações conhecidas

    Limite Melhoria
    E-mail já cadastrado devolve 500 (comportamento do material do curso) tratar a violação de unicidade e devolver 409 Conflict
    Hash com SHA-256 sem salt (como no hands-on) BCrypt ou Argon2, que são lentos de propósito e têm salt
