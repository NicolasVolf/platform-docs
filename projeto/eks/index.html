    EKS

    Página completa do grupo, com todos os comandos: EKS

    A plataforma roda num cluster Amazon EKS (eks-store, região us-east-2), com o banco do Account num Amazon RDS for PostgreSQL. Tudo fica no namespace store. O cluster é criado pelo eksctl a partir de um arquivo versionado e apagado quando não está em uso, porque é o item mais caro do projeto.

    Decisões

    Peça Escolha Por quê
    Kubernetes 1.37 versão padrão do EKS, em suporte padrão (as de suporte estendido custam 6× mais por hora)
    Nós 2× t3.medium, managed node group os requests de memória somam ~2,6 GiB; t3.small não deixava folga para rolling update nem para o teste de carga
    Rede VPC do eksctl, 2 zonas, nós só em sub-redes privadas os nós não ficam expostos; só o ELB recebe tráfego da internet
    Saída para a internet 1 NAT gateway os nós baixam imagens e o exchange chama a API de câmbio; um NAT por zona dobraria o custo
    Acesso ao cluster authenticationMode: API (access entries) permissões do Kubernetes dadas a roles da AWS sem editar o aws-auth
    Imagens ECR os pacotes do GHCR são privados; os nós já têm leitura no ECR
    Banco RDS PostgreSQL 17, db.t4g.micro, 20 GB gp3, sem acesso público a página do EKS do curso pede RDS ou DynamoDB; o security group aceita a porta 5432 só dos nós

    # Cluster EKS do projeto pna26 (criado com eksctl).
#   criar:  eksctl create cluster -f setup/eks-store.yaml
#   apagar: eksctl delete cluster -f setup/eks-store.yaml --disable-nodegroup-eviction
# Custo aproximado ligado: ~US$ 0,23/h (control plane 0,10 + 2x t3.medium 0,083
# + NAT gateway 0,045). Apagar quando não estiver em uso.
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: eks-store
  region: us-east-2
  version: "1.37"        # versão padrão do EKS, em suporte padrão até 11/2027

# eksctl cria uma VPC nova com sub-redes públicas (balanceador) e privadas (nós)
# em 2 zonas. O RDS também exige 2 zonas no subnet group.
availabilityZones: [ us-east-2a, us-east-2b ]
vpc:
  cidr: 10.20.0.0/16
  nat:
    gateway: Single      # 1 NAT só: os nós privados saem para a internet (ECR, APIs) por ele

accessConfig:
  authenticationMode: API   # quem acessa o cluster é definido por access entries

managedNodeGroups:
  - name: ng-store
    instanceType: t3.medium   # 2 vCPU / 4 GiB, até 17 pods por nó
    desiredCapacity: 2
    minSize: 2
    maxSize: 2
    volumeSize: 20
    privateNetworking: true   # nós só nas sub-redes privadas, sem IP público
    labels:
      role: store

    Manifestos dos meus serviços

    Cada serviço tem o próprio k8s/k8s.yaml (ConfigMap, Deployment e Service), como no exercício MiniKube e no Hands-on 5. Padrões que segui em todos:

    • Service ClusterIP com o mesmo nome do compose (account, auth): os Feign clients (http://account:8080) funcionam sem mudança;
    • container sem root (uid 1001), sem escalada de privilégio, /tmp num emptyDir;
    • requests/limits de memória e probes TCP na 8080;
    • nenhum Secret no Git: o pipeline faz kubectl apply -f k8s/ a cada deploy, e um Secret de exemplo ali sobrescreveria o real. account-secrets, auth-secrets e notification-secrets são criados uma vez por cluster, com a senha aleatória do RDS lida de um arquivo temporário (nunca na tela).

    # Account no EKS: só é acessível pelo auth e pelo gateway (ClusterIP), como no compose.
# O CI troca a imagem ":latest" pela tag do commit antes do kubectl apply.
#
# O Secret com usuário e senha do banco NÃO fica no Git. Crie uma vez por cluster:
#   kubectl create secret generic account-secrets -n store \
#     --from-literal=DATABASE_USERNAME=<usuario> \
#     --from-literal=DATABASE_PASSWORD=<senha>
apiVersion: v1
kind: ConfigMap
metadata:
  name: account-configmap
data:
  # endpoint do RDS PostgreSQL (rds-store). Para testar no Docker Desktop: postgres
  DATABASE_HOST: rds-store.cb046mq0wslp.us-east-2.rds.amazonaws.com
  DATABASE_PORT: "5432"
  DATABASE_DB: store
  # mensageria: o relay do outbox publica em account-events (platform/k8s/kafka.yaml)
  KAFKA_BOOTSTRAP_SERVERS: kafka:9092
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: account
  labels:
    app: account
spec:
  replicas: 1
  selector:
    matchLabels:
      app: account
  template:
    metadata:
      labels:
        app: account
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 1001
        runAsGroup: 1001
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: account
          image: 637423273088.dkr.ecr.us-east-2.amazonaws.com/account-service:latest
          # o CI sempre aplica uma tag nova (sha-xxxxxxx), então não precisa de Always
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef:
                name: account-configmap
            - secretRef:
                name: account-secrets
          readinessProbe:
            tcpSocket:
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: 8080
            initialDelaySeconds: 60
            periodSeconds: 10
          resources:
            requests:
              memory: "256Mi"
              cpu: "100m"
            limits:
              memory: "512Mi"
              cpu: "1"
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: [ "ALL" ]
          volumeMounts:
            # o Tomcat precisa de um /tmp gravável
            - name: tmp
              mountPath: /tmp
      volumes:
        - name: tmp
          emptyDir: {}
---
apiVersion: v1
kind: Service
metadata:
  name: account
spec:
  type: ClusterIP
  selector:
    app: account
  ports:
    - protocol: TCP
      port: 8080
      targetPort: 8080

    Permissões do CI no cluster

    O pipeline faz o deploy sozinho em todo push na main quando a variável da org EKS_CLUSTER existe. A role OIDC do CI (AWS) ganhou uma access entry com AmazonEKSAdminPolicy só no namespace store.

    No deploy de 16/11 apareceu um problema que a documentação da AWS não deixa claro: ao criar um Role (o do Prometheus), o Kubernetes confere se quem cria já tem todas as permissões que está dando (proteção contra escalada de privilégio). Essa conferência só olha o RBAC do próprio Kubernetes e não enxerga a access policy da AWS. A correção foi colocar a role num grupo store-deployers e dar a esse grupo o papel admin com um RoleBinding, só no store:

    aws eks update-access-entry --cluster-name eks-store --region us-east-2 \
  --principal-arn arn:aws:iam::637423273088:role/github-actions-pna26 --kubernetes-groups store-deployers
kubectl create rolebinding ci-store-admin -n store --clusterrole=admin --group=store-deployers
# conferência: "yes" no store e "no" fora dele
kubectl auth can-i create roles -n store   --as=ci --as-group=store-deployers
kubectl auth can-i create roles -n default --as=ci --as-group=store-deployers

    Problemas encontrados

    Problema Solução
    docker login no ECR falha no Windows (token grande demais para o Gerenciador de Credenciais) docker-credential-ecr-login em credHelpers
    infra falha ao criar o Role do Prometheus (anti-escalada do Kubernetes) grupo store-deployers + RoleBinding para admin no store
    exchange devolve 503 no EKS a API de câmbio gratuita responde 429 para IPs da AWS; o exchange do Gabriel trata com cache e 503
    gh variable set --org devolve 403 escopo admin:org no gh só enquanto precisa, removido depois
